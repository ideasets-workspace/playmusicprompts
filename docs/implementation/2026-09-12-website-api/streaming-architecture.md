## Recommended service boundaries

```text
Guest or account -> Website API -> durable generation job -> private Google music API
                                            |
                                  delivered take references
                                            v
                                  durable ingestion worker
                       restricted source fetch / validation / SHA-256
                                            |
                           private master asset + track catalogue
                                            v
                               deterministic packaging worker
                          versioned HLS renditions + media metadata
                                  /                      \
                on-demand playback session        station schedule
                                  \                      /
                            stream authorization + ad orchestration
                                            |
                            CDN manifests / segments -> player adapter

Account + verified reward -> download entitlement -> protected download derivative
```

**Our server owns ingestion, identity, catalogue, schedules, and entitlements; CDN origins own delivery bytes.** It is not necessary for every listener byte to pass through the web application's process. This separation satisfies server-owned storage and supports future clients without putting the private generation key into a player.

Keep these interfaces provider-neutral: `AssetStore`, `PackagingService`, `PlaybackGrantIssuer`, `StationScheduler`, `AdSessionProvider`, and `RewardVerifier`. They name real operational boundaries; an unconfigured adapter must report unavailable, never pretend to deliver.

## Ingestion and durable catalogue contract

1. Commit generation outcome and an ingestion task atomically. Use a unique `(upstream_request_id, take_number)` logical track key. Durable states distinguish `GENERATING`, `GENERATED`, `INGESTING`, `PACKAGING`, `READY`, and actionable failures. A copy failure preserves the generated result; it does not submit generation again.
2. Accept source references only from that job's server-held upstream response. Clients submit a prompt/options or a track ID, never a URL to proxy. Restrict fetches to the configured HTTPS delivery host, exact allowed bucket and delivery prefix, default TLS port and expected object identity. Disable redirects, bound bytes/time/concurrency, deny internal/loopback/link-local destinations and unexpected URL userinfo. Keep signed query strings and credentials out of logs. This is a positive allowlist, not a suffix check or an arbitrary-URL downloader. [OWASP SSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)
3. Renew an expired delivery URL from the recorded `gcs_uri` through the private API, then retry the **copy** with bounded backoff. Do not retry paid generation for a storage outage. The Google OIDC bearer and website API key go to the music API only, never to the media-fetch origin.
4. Stream bytes into a private temporary asset; compute full SHA-256 and byte count; validate actual audio container, decodability, stream count, duration and finite measurements. Use a worker process with resource limits to probe/transcode untrusted media. Filename/MIME is not proof of codec. A raw variation remains identified as raw and unavailable to automatic broadcast until the required master qualification succeeds.
5. Commit the private asset only after integrity and probe success. Store asset by content hash, with a separate logical track reference. One asset may back distinct provenance/ownership rows without conflating those users or jobs. S3 `PutObject` can validate a supplied full-object SHA-256. Multipart SHA-256 is a **composite** checksum; never compare it as though it were our full byte-stream digest. Retain checksum algorithm/type separately and verify like with like. [S3 upload integrity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html)
6. Build versioned renditions from the immutable master and retain encoder/profile versions. Mark `READY` only when all mandatory rendition files and manifest references are complete and validated. Publish the manifest last. Recover interrupted tasks from durable state after restart; quarantine or clean task-owned partial files without deleting another job's data.

Minimum persisted entities (proposed names, not claims of existing schema):

| Entity | Required invariant / fields |
|---|---|
| `generation_jobs` | Actor ID, request and idempotency key, request hash, upstream request/job IDs, outcome/shortfall, timestamps; sensitive response stored privately |
| `tracks` | Stable public ID, generation job/take unique key, creator guest/account identity, asset ID, display title, private prompt/facets, take provenance, visibility/reuse eligibility, moderation/quality state |
| `media_assets` | Unique byte SHA-256, byte size, verified format/duration/channels/sample rate, private storage key, source locator and copy state; no public master URL |
| `renditions` | Asset ID + encoding profile/version unique key, manifest/segment prefix, codec/container, measured size/duration, processing state, verification facts |
| `stations` / `station_programs` | Taxonomy, policy/version, stable schedule/program IDs, track asset version, UTC start/end, track boundaries, ad opportunities and revision |
| `playback_sessions` | Guest/account subject, device capabilities, scope, expiry, manifest provider, renewal policy; no access to master/download prefixes |
| `download_entitlements` | Authenticated user, track and export format, verified reward transaction, unique redemption, expiry, revocation and delivery state |

Store full metadata server-side for future similarity/reuse, but return a deliberately reduced public track object. Guest ownership uses a signed, unpredictable visitor session rather than an editable browser-provided user ID. Saving a playlist requires account identity as the latest owner instruction states; a guest listening queue is transient playback state, not a saved account playlist. Catalogue reuse eligibility is a separate flag from public visibility and must preserve privacy/moderation decisions. Do not silently turn private custom lyrics into a public radio source.

## Streaming, codecs, and station timing

Use **AAC-LC stereo HLS as the common first delivery profile**, with platform-validated packaging variants. Keep higher-quality master/download exports separate. Bitrate ladders, segment duration and output sample rate are explicit versioned profiles to be selected by listening and startup/rebuffer measurements; this report does not invent a perceptual-quality score or declare one bitrate universally transparent. Apple requires a stereo AAC-family option and permits multiple stereo bitrates; Android Media3 supports HLS with MPEG-TS, fMP4/CMAF and ADTS/AAC, subject to the device sample decoder. [Apple authoring specification](https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices/), [Android Media3 HLS](https://developer.android.com/media/media3/exoplayer/hls)

For initial owned web playback, a validated progressive AAC/MP3 rendition with proper HTTP Range handling is useful where HLS is unavailable; label its real delivery mode. It does not establish adaptive delivery or SSAI. Do not serve full WAV masters as the guest streaming shortcut.

A **station** is a server-clock schedule shared by listeners; joining selects the current program and offset. A personal queue continues from that person's position. Do not label an `ended -> next` browser queue as a synchronized live broadcast. For HLS assembly, maintain consistent codec/container/sample rate/channel count and aligned rendition boundaries, valid sequence/discontinuity handling, actual measured `EXTINF`, and an explicit clock/metadata endpoint. Transcode ads into compatible profiles before splicing. For scheduled programs, AWS requires ad breaks to align with segment boundaries and warns that mismatches can skip the break. The opened AWS guide provides an assembly test procedure; an **audio-only channel using our assets is still a production acceptance test**, not a fact established here. [AWS channel setup and validation](https://docs.aws.amazon.com/mediatailor/latest/ug/channel-assembly-getting-started.html)

Track-to-track overlap is an optional personal-listening feature. Crossfading every song cannot be assumed compatible with fixed linear schedules, ad impressions or a single native HLS timeline. Finish music before an ad break, keep ads outside user music effects, handle no-fill/error by resuming music, and expose truthful now-playing/ad state. Do not loop failed ads or require a reward video merely to continue listening.

## Authorization across manifests, segments and downloads

- Private S3 origins must be inaccessible directly; CloudFront origin restrictions and viewer authorization are separate layers. OAC by itself does not make viewer URLs private. [CloudFront private-content model](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/PrivateContent.html)
- In the GCP alternative, Cloud CDN does **not** reject a request just because the signature/cookie is absent. Configure a private GCS origin and the CDN's required service identity, or an origin that rejects unsigned access and validates the needed signed requests. Test unsigned origin and CDN access explicitly; adding a signing key is not the entire protection. [Cloud CDN security considerations](https://docs.cloud.google.com/cdn/docs/using-signed-urls)
- GCP signed-cookie `URLPrefix` is a textual prefix: `/data` also matches `/database`. Scope with deliberate trailing `/` boundaries and do not copy CloudFront wildcard syntax. These are separate token formats. [Cloud CDN signed cookies](https://docs.cloud.google.com/cdn/docs/using-signed-cookies)
- Guest access is still scoped: a guest obtains an expiring **playback** grant, not a Google credential and not a download entitlement. Gate all variant manifests, media segments, initialization files and encryption keys, if present. Signing only the top-level `.m3u8` does not authorize or protect every child URI.
- On web, a same-site media domain with scoped CloudFront signed cookies can cover the playback asset prefix. Cookie support and renewal must be tested per native TV/mobile adapter; where unavailable, use an explicitly supported signed-URI/manifest-auth design for every referenced resource. Do not assume a query signature propagates from a parent manifest. CloudFront checks each request's expiry, including Range requests, so renew before the next fetch fails. [CloudFront signed-cookie behavior](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-cookies.html)
- Use separate origin paths/cache behaviors for masters, playback renditions and downloads. Never grant a wildcard that includes all three. Authorize a track before issuing a delivery token, bind to stable IDs, cap abuse at the session edge, and avoid logging bearer query strings.
- A download grant is created only for a logged-in user and a supported, actually verified rewarded-ad completion. Persist transaction/nonce/user/track binding and reject replay, mismatched user, expiry, duplicate transaction and client-only `completed:true`. Google web and native verification capabilities are not assumed identical; parent monetization audit owns the concrete supported mechanism. With no trustworthy reward verification configured, the paid-reward entitlement path remains unavailable rather than accepting a timer or UI event as proof.
- Redeeming an entitlement once and issuing a short-lived CDN link are different properties: the CDN link may be reusable until its expiry. A truly single-use download needs an enforcing token gateway, with a deliberate resumable-Range policy. Do not describe ordinary signed CDN URLs as single-use.
- Streaming does not make audible content impossible to save: authorized playback exposes decodable media and can be recorded. Tokenization, private masters, expiration and optional compatible DRM reduce unauthorized redistribution; they cannot justify a promise that music is uncopyable. The reward gates the authorized download product.

### Protected HLS can retain a shared segment cache

CloudFront signed cookies support wildcard resources and validation before serving an edge-cached object; signed-cookie attributes do not themselves create separate cached copies. A signed cookie's **custom authorization policy** is different from a CloudFront **custom cache policy**. Conflating those names would incorrectly conclude that Pro cannot use wildcard signed-cookie authorization. Use narrow listening prefixes, short grants with renewal and private origins. Keep original/download masters outside every listening grant. [Use signed cookies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-cookies.html) — full technical page read.

AWS's basic MediaTailor integration uses managed `CachingDisabled` plus `AllViewer` for personalized manifests, and managed `CachingOptimized` for media/ad segments. Thus custom cache policies are **not universally required** for a safe basic HLS/SSAI topology. Immutable segments should use stable URLs across listeners; viewer-specific manifests must not be shared. The basic guide's segment JSON example differs from its prose in origin-request handling, so it is not a deployment artifact to copy without review. [MediaTailor basic CloudFront integration](https://docs.aws.amazon.com/mediatailor/latest/ug/cloudfront-basic-setup.html) — full relevant guide including example read; its linked Markdown view failed with unsupported content type, HTML succeeded.

Our proposed routing contract is: public app assets → app origin; guest/session grant endpoint → uncached app backend; personalized manifests → uncached manifest service; content segments → private rendition origin with viewer authorization; ad segments → ad origin with the required measurement semantics; masters → a separate narrowly authorized download path. Verify route precedence against actual URLs, not merely extensions. The startup manifest, every nested playlist, segments and any key/init resources must share the intended access boundary. Do not let the content origin offer an unsigned bypass around scheduled ad sessions.

A further web-specific trap: the recommended managed CORS response policy supplies wildcard origins and does not add credential permission. Cookie-bearing cross-origin playback therefore needs a deliberately verified same-origin route or appropriate origin/edge CORS handling; generic managed CORS is not proof of browser compatibility. Origin-provided headers can override that policy's CORS values. This is a concrete configuration acceptance test, not grounds for declaring a hard Business minimum. [Managed response-header policies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-response-headers-policies.html) — full technical policy tables read. No actual flat-plan signed-cookie playback was tested here.

### HLS request arithmetic: bytes alone select the wrong tier

**Illustrative input, not forecast:** 100,000 listener-hours/month; one audio rendition at 192,000 bits/second; no video. Encoded payload is `100000 × 3600 × 192000 / 8 = 8,640,000,000,000 bytes`: **8,640 decimal GB or 8,046.627 GiB**. This excludes container overhead, HTTP headers, manifests, ads, retransmissions, prefetch discarded by skips and official downloads. Cloud CDN explicitly meters GiB and includes HTTP response headers/body/trailers. AWS's CloudFront billing guidance distinguishes billed gigabytes from raw-byte usage but did not establish the flat-plan GB/TB binary conversion in the inspected material. Preserve both units and do not assert equivalence. Either convention leaves this payload below 50TB. [Google network/CDN pricing](https://cloud.google.com/vpc/network-pricing), [CloudFront billing reports](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/reports-billing.html) — relevant metering sections read; exact AWS conversion **UNKNOWN**.

Let `d` be segment seconds and `r` playlist-refresh seconds. A conventional live single-rendition model is `requests/hour = 3600/d + 3600/r + startup/ads/retries/other`. The table excludes that last term:

| Audio HLS scenario | Segment GETs/hour | Playlist GETs/hour | Total/hour | Total at 100,000 hours |
|---|---:|---:|---:|---:|
| 6s segments, 6s live refresh | 600 | 600 | 1,200 | 120M |
| 6s segments, 3s refresh sensitivity envelope | 600 | 1,200 | 1,800 | 180M |
| 4s segments, 4s live refresh | 900 | 900 | 1,800 | 180M |
| 4s segments, 2s refresh sensitivity envelope | 900 | 1,800 | 2,700 | 270M |
| 6s on-demand track, immutable VOD playlist | 600 | Per track/start, not periodic | At least 600 | At least 60M |
| 4s on-demand track, immutable VOD playlist | 900 | Per track/start, not periodic | At least 900 | At least 90M |

RFC 8216 §6.3.4 requires waiting at least a target duration after a changed playlist and half a target duration after an unchanged reload. It exempts fixed VOD playlists from recurring reloads. The half-target rows are a conservative sensitivity envelope, **not a claim that compliant healthy clients continuously fetch at that frequency**, nor measured client behavior. Long-lived unchanged manifests can indicate stalls. Actual native/JS player request traces must replace these models. [RFC 8216, §6.3.4](https://www.rfc-editor.org/rfc/rfc8216.html#section-6.3.4) — complete reload section and adjacent relevant playlist rules read; the entire RFC was not reread for this follow-up.

At 6s/6s, Pro's 10M baseline corresponds to roughly **8,333 listener-hours**, before overhead. Business's 125M corresponds to **104,167 hours**, leaving only 5M requests above the hypothetical 100,000-hour base. The 4s live base already exceeds Business. Conversely, individualized VOD sessions could fit Business's request baseline comfortably with 6s segments, subject to actual starts, skips and unrelated traffic. Premium's 500M adds request headroom and failover features; it is not automatically necessary for on-demand use. All values are arithmetic over published allowances, not promises of guaranteed capacity.

Caching reduces origin work and origin bytes, **not the number of viewer requests arriving at the CDN**. Cache-hit ratio cannot rescue an undersized request allowance. Reducing manifest refresh below the declared protocol/client contract merely to fit a plan would damage playback. HTTP/2 multiplexing also does not turn many HTTP requests into one billable request.

### Decision invalidators and remaining acceptance evidence

1. **Traffic semantics:** user confirmation or product evidence that everyone must hear the same clock-synchronized station increases the value of managed Channel Assembly/SSAI; per-user generated queues do not establish that need.
2. **Economics:** actual request traces, geography, retention, generation/download volume or a negotiated CDN offer can reverse a GCP-first cost/operations tradeoff. Compare identical listening and security behavior. Preserve separate VOD and live request models.
3. **Operational evidence:** recovering a maintained, secure AWS production source/deployment could erase much of the assumed extra AWS implementation work. Historical resource IDs alone do not establish that advantage.
4. **Media/ad acceptance:** a real pure-audio Channel Assembly plus Google ad test, or verified GCP pure-audio Stitcher support, changes the managed-service comparison. Google ad eligibility and downloadable reward policy remain independent requirements.
5. **Security/device compatibility:** a failing signed-cookie/CORS/native-TV test, unsigned origin bypass, or shared personalized-manifest cache invalidates a deployment even if its nominal price is attractive.
6. **Commercial terms:** account flat-plan eligibility, a resolved MediaTailor delivery waiver, actual SLA coverage, GCP Preview allowlisting/GA changes or AWS unit clarification may change the recommendation or its cost range.
