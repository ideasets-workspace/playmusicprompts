# Outcome first

1. **Architecture (committed, §F2/§F8): Auth.js v5 (next-auth) with the Prisma adapter, in a dedicated Next.js route surface served at `https://auth.playmusicprompts.com`, database sessions, our Postgres as the sole user store.** It is the only option in the comparison that (a) keeps the user directory in the project's own Postgres by construction (S-12 shows the adapter writing `User/Account/Session/VerificationToken` — the exact four models already in `schema.prisma`, L-01), (b) costs $0 in vendor MAU fees, (c) supports Google out of the box and any OAuth 2.0 provider — Login with Amazon included — through the documented custom-provider object (S-13: "We support any OAuth or OIDC compliant provider"), and (d) needs no second server process on the EC2 host. Falsifier and the one genuine open point are in §F8.
2. **Hosted IdPs fail the "own database" requirement by construction**: Cognito user pools own the directory and their custom domain requires an ACM certificate in **us-east-1** and a Cognito-managed CloudFront distribution you cannot configure (S-20); Identity Platform charges per MAU above 50,000 (S-21). Both are documented, not rejected on taste. Auth0/Clerk/Supabase are paid vendors — `PAID-VENDOR FLAG`.
3. **Mobile: Google on Android must NOT use a custom-scheme OAuth redirect.** Google's own native-app doc, updated 2026-08-07, states "Custom URI schemes are no longer supported on Android and Chrome apps" and "Custom URI schemes are no longer supported due to the risk of app impersonation" (S-05). Therefore the Flutter app uses `google_sign_in` 7.2.0 (Credential Manager on Android, S-15/S-16) to obtain a Google ID token, and our server validates it (`iss`, `aud`, `exp`, JWKS — S-18) and creates the Auth.js session. For Login with Amazon on mobile, Amazon's SDKs open the system browser / Safari View Controller / Amazon-app secure context (S-31, S-34) — RFC 8252-conformant external user-agents — and the server verifies the access token via `https://api.amazon.com/auth/o2/tokeninfo` and checks `aud` equals our client ID (S-09).
4. **Store rules are binding additions** (§F5): Apple §4.8 (text dated June 8, 2026, S-03) requires an *equivalent* login service with three named properties when Google/Amazon login sets up the primary account — Sign in with Apple satisfies it, so it is a **new mandatory item for the iOS build that Berk must decide** (Apple does not name its own service as the only way; the three criteria are quoted in §F5). Apple §5.1.1(v) and Google Play's User Data policy both require **in-app account deletion**; Play additionally requires a **web link** for deletion requests (S-22).
5. **Password policy contradiction preserved** (§Contradictions): NIST SP 800-63B rev. 4 (S-23) — minimum 15 characters for single-factor, **no composition rules**, **no periodic change**, blocklist check; versus KVKK's 15 Feb 2022 public announcement (S-35) — minimum 10 characters **with** upper/lower/digit/special composition and periodic change reminders. OWASP ASVS 5.0 sides with NIST (S-24 §6.2.1, §6.2.5, §6.2.10). The report recommends the NIST/ASVS posture and names the KVKK deviation for Berk's decision, because Türkiye is a served market.
6. **Passkeys/WebAuthn are the 2026 "most advanced" bar**: NIST 800-63B-4 requires a phishing-resistant option at AAL2 and names WebAuthn/FIDO2 as phishing-resistant via verifier-name binding (S-23 §3.2.5); syncable passkeys are permitted below AAL3 (S-23 App. B). Recommended as phase 2 after Google/Amazon/email launch (§F1).

# Findings by subquestion

## F1. Requirements extraction and what "most advanced and secure" means in 2026 primaries

Requirements extracted from Berk's order (his words, then my reading): (1) "kendi user veritabanımız olsun" → the user directory lives in our Postgres — a hosted IdP that owns the directory does not satisfy this; (2) "google ve amazon authentication ı destekleyelim" → Google and Login with Amazon federation, mandatory; (3) an own database implies a first-party credential (email + password) as well, otherwise the database holds only federated identities — treated as mandatory, consistent with `passwordHash String?` already in `User` (L-01); (4) "auth.playmusicprompts.com gibi yapı" → a dedicated auth subdomain; (5) "hem web hem de mobil ve tablet appler" → web + Android + iOS + tablet; (6) "en ileri seviyede ve güvenli" → the 2026 primary-source bar below; (7) "google cloud … proje yarat playmusicprompts … authentication parametrelerini ekle" → a GCP project named `playmusicprompts` holding the OAuth consent screen and client IDs (§F3, §F8).

What the 2026 primaries define as the bar:
- **PKCE everywhere.** RFC 9700 §2.1.1: "Public clients MUST use PKCE"; for confidential clients "the use of PKCE is RECOMMENDED"; "Authorization servers MUST support PKCE"; §2.1.1 also: S256 is "the only such method" that does not expose the verifier (S-02). RFC 8252 §6: "Public native app clients MUST implement … PKCE" (S-01).
- **Refresh-token rotation or sender-constraining for public clients.** RFC 9700 §2.2.2 / §4.14.2: "Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation" (S-02).
- **Sender-constrained access tokens SHOULD be used** — mTLS (RFC 8705) or DPoP (RFC 9449); RFC 9700 §2.2.1 (S-02). Google's web-server doc already describes DPoP-bound refresh tokens ("If DPoP was used, the refresh token is bound to the private key", S-26) — so DPoP is live at one of our two IdPs. RFC 9449's own text was not read (timeout) → DPoP details are `[single-source via S-02]`.
- **Exact redirect-URI matching; no open redirectors; no 307.** RFC 9700 §2.1, §4.1.3, §4.11, §4.12 (S-02). Google enforces it: "the http or https scheme, case, and trailing slash ('/') must all match" (S-26).
- **Password grant is dead.** RFC 9700 §2.4: "The resource owner password credentials grant MUST NOT be used" (S-02).
- **Phishing-resistant authentication (passkeys/WebAuthn).** NIST SP 800-63B-4: "Verifiers SHALL offer at least one phishing-resistant authentication option at AAL2"; WebAuthn/FIDO2 named as phishing-resistant through verifier-name binding; "Passwords are not phishing-resistant"; OTP "SHALL NOT be considered phishing-resistant"; syncable authenticators allowed except at AAL3 (S-23 §2, §3.1.1, §3.2.5, App. B).
- **Password rules (NIST 800-63B-4 §3.1.1, S-23):** minimum 15 characters when single-factor (8 when part of MFA); SHOULD allow ≥64; SHALL NOT impose composition rules; SHALL NOT require periodic change (but SHALL force change on evidence of compromise); SHALL check against a blocklist of commonly used/expected/compromised passwords; no hints. Rate limiting: "no more than 100" consecutive failed attempts per authenticator before disabling (§3.2.2).
- **OWASP ASVS 5.0 V6 (S-24):** 6.2.1 ≥8 chars, 15 strongly recommended; 6.2.4 check against ≥ top-3000 list; 6.2.5 no composition rules; 6.2.7 paste and password managers permitted; 6.2.9 ≥64 permitted; 6.2.10 no periodic rotation; 6.2.12 breached-password check; 6.3.1 credential-stuffing/brute-force controls; 6.3.6 email is not an authentication factor (L3); 6.3.8 no user enumeration via errors/timing; 6.4.2 no secret questions.
- **KVKK (Türkiye) — S-35, 15 Feb 2022:** recommends two-factor authentication offered from sign-up, login notification on new devices, HTTPS, current hashing algorithms, per-IP failed-attempt limits, showing users their last ≥5 successful/failed logins, password policy with periodic change reminders, no reuse of last 3 passwords, CAPTCHA, ≥10-character passwords with upper/lower/digit/special mix. These are "tavsiye" (recommendations) made "kendi risk değerlendirmelerini yaparak" (subject to the controller's own risk assessment) — quoted in §Contradictions.
- **Data minimisation:** the only Google scopes needed are `openid email profile`; the only LwA scope needed is `profile` (name, email, user_id per S-08/S-31) — `postal_code` is not needed and should not be requested.

## F3. Google sign-in specifics (quoted)

- **Verification / consent screen.** "If your app utilizes only non-sensitive scopes, it is not mandatory for your app to complete the app verification process. However, if you want your app to display an app name and logo on the OAuth consent screen, you will need to complete a lighter-weight verification process known as 'brand-verification'" (S-04). We need only `openid email profile` → no sensitive-scope verification; brand verification only for the logo. The consent-screen "publishing status / testing vs production" help page timed out → `[UNVERIFIED this session]`; the parent must open `support.google.com/cloud/answer/10311615` before configuring.
- **Client types (S-05, updated 2026-08-07).** Web application client: authorised JavaScript origins + authorised redirect URIs, exact match including "scheme, case, and trailing slash" (S-26). iOS client: "Enter the bundle identifier … the value of the CFBundleIdentifier key"; optional App Store ID; Team ID "required if you are enabling App Check"; bundle ID "must not include the asterisk"; App Check uses Apple App Attest (S-05). Android client: the subsection was not read this session (`[UNVERIFIED]` — the register notes S-05 as `[PARTIAL]`); pub.dev's Android README confirms the server side needs the **web** client ID as `serverClientId` and that "Missing or incorrect signing SHA for one or more build configurations" is the top configuration error (S-16).
- **Custom URI schemes on Android are gone.** "Note : Custom URI schemes are no longer supported on Android and Chrome apps" and "Custom URI schemes are no longer supported due to the risk of app impersonation"; loopback redirect "DEPRECATED for Android, Chrome app and iOS OAuth client types" (S-05). Consequence: on Android, Google sign-in in Flutter must go through `google_sign_in` (Credential Manager, S-16), not through `flutter_appauth` against `accounts.google.com`. On iOS the custom scheme `com.googleusercontent.apps.<client-id>` remains documented (S-05 redirect_uri table), and `google_sign_in_ios` is the endorsed path (S-15).
- **Flutter package facts (S-15):** `google_sign_in` 7.2.0, Android SDK 21+, iOS 12.0+, Web any; `GoogleSignIn.instance.initialize(clientId:, serverClientId:)`; `attemptLightweightAuthentication()`; on web "user-initiated sign in on web must use a button rendered by the sign in SDK"; web access tokens are not refreshed and "expire after 3600 seconds"; `authorizeServer(scopes)` yields a server auth code "not always available on all platforms". BSD-3-Clause.
- **ID-token validation on our server (S-18, updated 2025-12-22):** verify signature with Google's JWKS (rotate per `Cache-Control`), `aud` ∈ our client IDs, `iss` ∈ {`accounts.google.com`, `https://accounts.google.com`}, `exp` not passed; "Only use Google ID token `sub` field as identifier … don't use email address as an identifier"; with GIS on web, validate the `g_csrf_token` double-submit cookie; use `google-auth-library` `verifyIdToken()` in Node. Google is authoritative for the email only when it ends in `@gmail.com` or `email_verified` is true with `hd` set (S-18).

## F5. Flutter mobile OIDC, token storage, store rules

- **RFC 8252 (S-01) governs the mobile shape:** native apps "MUST use an external user-agent" (§5); "MUST NOT use embedded user-agents" (§8.12); PKCE mandatory for public native clients (§6); the AS "MUST offer at least the three redirect URI options" — private-use scheme, claimed https, loopback (§7); claimed "https" URIs "SHOULD" be preferred "where possible" (§7.2: Universal Links / App Links, App. B.1–B.2); a unique redirect URI per authorization server is "REQUIRED" for mix-up defence (§8.10); public clients MUST be registered as such and redirect URIs matched exactly except loopback port (§8.4); no static client secret in the app (§8.5).
- **`flutter_appauth` 12.1.0 (S-17, BSD-3-Clause, published "4 days ago" relative to 2026-09-03):** wraps AppAuth iOS/Android; `authorizeAndExchangeCode(AuthorizationTokenRequest(clientId, redirectUrl, discoveryUrl|issuer|serviceConfiguration, scopes))`; PKCE handled by AppAuth; `token(...)` for refresh; `endSession(...)`; `preferEphemeralSession` on iOS ≥13; Android `appAuthRedirectScheme` manifest placeholder (lowercase) or an `intent-filter` on `RedirectUriReceiverActivity` (this is how an **App Link https redirect** is declared); iOS `CFBundleURLTypes`. - **Google on Flutter:** `google_sign_in` 7.2.0 (S-15) → Android via Credential Manager (S-16), iOS via `google_sign_in_ios`; send the ID token to `auth.playmusicprompts.com`, verify per S-18, mint our session. **Amazon on Flutter:** Amazon SDK flows (S-31, S-34) via platform channels or a licence-checked community bridge (`[UNVERIFIED]`), then server-side `tokeninfo` + `profile` (S-09).
- **Token storage:** RFC 9700 §4.10.1 notes sender-constrained tokens still leak when "an attacker gets access to the token and the key material … corrupted client software" — so keep tokens in the platform keystore (iOS Keychain / Android Keystore). The `flutter_secure_storage` page was **not opened** this session → package facts `[UNVERIFIED]`; the parent must read it before choosing it.

## Five-part academic records (each [FULL] primary)

### R9 record — RFC 8252, OAuth 2.0 for Native Apps (S-01, BCP 212, October 2017, `[FULL]`)
1. **Problem in the authors' framing:** native apps historically ran OAuth in embedded web-views, which lets "the host app … copy user credentials and cookies" and forces users "to authenticate from scratch in each app" (§4); OAuth servers "that assume all clients are confidential web clients" need to understand public native clients (§4).
2. **Method:** authorization request opened in an external user-agent (browser / in-app browser tab) with the code grant + PKCE; response returned via one of three redirect URI classes — private-use scheme `com.example.app:/oauth2redirect/example-provider`, claimed https `https://app.example.com/oauth2redirect/example-provider`, loopback `http://127.0.0.1:{port}/{path}` (§7.1–7.3); server-side rules: record client type, exact redirect match (port excepted for loopback), reject schemes without a "." (§8.4); state for cross-app request forgery (§8.9); per-AS unique redirect for mix-up (§8.10). Normative flow: Figure 1 steps (1)–(6).
3. **Real numbers:** the RFC has no empirical tables (stated per R9). Quantities it fixes: 3 mandatory redirect classes (App. A items 1–3); UWP scheme length limit 39 characters (App. B.3); Android App Links "Android 6.0 and above", iOS Universal Links "iOS 9 and above" (App. B).
4. **Stated limitations:** private-use schemes let "multiple apps … register the same scheme", so interception is possible and PKCE is the mitigation (§8.1); loopback "may be susceptible to interception by other apps" (§8.1); App. B "will likely change over time" and is non-normative; fake external user-agents remain possible (§8.7). Analyst-identified: Google has since withdrawn custom-scheme support on Android (S-05), so §7.1 is no longer usable with Google on Android — the RFC's platform appendix is out of date there.
5. **Application here:** Flutter app = public client, no embedded secret (§8.5); use `google_sign_in` on Android (S-05 ban) and AppAuth-style flow with **claimed https App Links/Universal Links** against `auth.playmusicprompts.com` for our own OIDC-style endpoints (§7.2 SHOULD); distinct redirect paths per provider (§8.10); PKCE S256 everywhere; server registers exact redirect URIs (§8.4).

### R9 record — RFC 9700, Best Current Practice for OAuth 2.0 Security (S-02, BCP 240, January 2025, `[FULL]`)
1. **Problem:** "OAuth implementations are being attacked through known implementation weaknesses and anti-patterns"; OAuth is used in higher-security and more dynamic settings than RFC 6749/6819 assumed; browser fragment handling changed the implicit grant's security model (§1).
2. **Method:** an updated attacker model A1–A5 (web attacker, network attacker, reader of authorization response, reader of authorization request, holder of an access token, §3) and, per attack, countermeasures: exact redirect matching (§4.1.3), Referrer-Policy/form-post (§4.2.4), mix-up via `iss` (RFC 9207) or distinct redirect URIs (§4.4.2), PKCE or OIDC nonce against code injection (§4.5.3), PKCE-downgrade rule "a token request containing a code_verifier … accepted only if a code_challenge parameter was present" (§4.8.2), sender-constrained tokens via mTLS/DPoP and audience restriction (§4.10), refresh-token rotation/sender-constraining for public clients (§4.14.2), 303 not 307 (§4.12), CSP `frame-ancestors` (§4.16), exact-origin postMessage (§4.17.2). Normative summary in §2.
3. **Real numbers:** no empirical tables (stated). Fixed values: CSP "level 2 … or greater" (§4.16); HTTP 303 vs 307 (§4.12); formal-analysis provenance cited: arXiv 1601.01229 and 1704.08539 (§3, §4.4.1); implementation-failure evidence cited from research.ubc (CCS'12) and research.cmu (CCS'14) that "a large portion of client implementations do not or fail to properly implement security controls, like state checks" (§4.10.3).
4. **Stated limitations:** "following the best practices described in this document may break interoperability" (§1); PKCE/nonce protection is circumventable if the attacker can modify the victim's `code_challenge`/`nonce` before the victim's session (§4.5.4); sender-constrained tokens are undermined when both token and key material leak, e.g. XSS or corrupted client software (§4.10.1); "Architecture and performance reasons may prevent" sender-constraining in some deployments (§4.10). Analyst-identified: DPoP details live in RFC 9449, not read here.
5. **Application here:** the §F7 checklist rows C1–C11 are direct transcriptions; two authorization servers (Google, Amazon) make §4.4.2 mix-up defence mandatory for us; refresh-token rotation with family revocation for the Flutter client (C8); DPoP for app↔API as phase 2 (C9); the `LoginEvent`-driven throttling and no-open-redirector rules on `auth.` and `www.`.

# Contradictions, corrections, uncertainty, gaps

**Contradiction 1 — password policy.** NIST SP 800-63B rev.4 (S-23, page timestamp 26 Aug 2025): "Verifiers and CSPs SHALL require passwords … to be a minimum of 15 characters in length"; "SHALL NOT impose other composition rules"; "SHALL NOT require subscribers to change passwords periodically". OWASP ASVS 5.0 (S-24): 6.2.5 "passwords of any composition can be used, without rules limiting the type of characters"; 6.2.10 "must not require periodic credential rotation". KVKK public announcement (S-35, 15 Şubat 2022): "parolaların uzunluğunun asgari 10 karakter olması, büyük-küçük harf, rakam ve özel karakterlerin bir arada kullanılmasına yönelik güçlü parola oluşturulmasının sağlanması" and "parolaların belirli aralıklarla değiştirilmesinin sağlanması veya bu hususun ilgili kişilere hatırlatılması". KVKK frames these as recommendations to be adopted "kendi risk değerlendirmelerini yaparak" (after the controller's own risk assessment). Not averaged: the report recommends the NIST/ASVS posture (longer minimum, blocklist, no composition, no rotation) and records the KVKK deviation as **D-2 for Berk**. The KVKK text also aligns with NIST on several points (2FA offered from sign-up, per-IP throttling, current hashing, HTTPS) — those are adopted without conflict.

**Contradiction 2 — RFC 8252 vs Google on Android redirects.** RFC 8252 §7.1/App. B.2 (2017) describes private-use schemes as broadly supported on Android; Google (S-05, 2026-08-07) no longer supports them for its OAuth clients on Android/Chrome apps. Resolution: platform vendor's current rule wins for the Google IdP; the RFC remains correct for our **own** authorization endpoints.

**Correction — table name.** The slice file says `LoginAttempt`; disk (L-01) has `LoginEvent`. Reported, not silently fixed.
