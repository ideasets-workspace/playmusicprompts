# Outcome first

Eight facts decide the rebuild (each traced in the Claim ledger, C-numbers):

1. **The create surface has converged on prompt box + Simple/Custom toggle + Instrumental toggle + dice/inspire chips + two takes per run** (Suno official help, Udio official help, plus three independent 2026 reviews; C1). Nobody exposes a numeric control on the casual surface; every leader hides numbers behind Custom/Advanced (extends the 2026-08-29 study, unchanged).
2. **The 2026 frontier moved from "prompt → song" to "section-level co-editing"**: ElevenLabs Composer (section timeline, per-section include/exclude styles, multiple takes per section), Suno Studio 2.0 (chat bar over a multitrack timeline, Take Lanes, keystrokes Space/Shift-R/Shift-C/Cmd-L), Adobe Premiere 27.0 beta Generate Music (BPM or auto, 5 s–5 min, 4 variations, loop), ProducerAI→Google Labs (conversational agent, 2026-02-24). Our composer must expose *structure* as an editable object, not only a prompt (C2, C3, C4).
3. **Every platform player of 2026 is converging on the same skeleton**: persistent bottom bar + right-side "Now Playing" context panel (Spotify desktop 3-column, Apple Music web beta floating bottom bar 2026-04-30) or split-view Now Playing with Up-Next queue embedded (YouTube Music 2026-04, Tidal 2026-05). Lyrics moved INTO Now Playing (Spotify, YTM). Queue is reorderable by drag with an explicit "Clear queue" confirmation (Spotify support) (C5).
4. **The spec settles our measured AnalyserNode-zeros fact**: W3C Web Audio API 1.1 Editor's Draft (26 Aug 2026) §1.22.4: "a MediaElementAudioSourceNode MUST output silence ... if ... the fetch algorithm labeled the resource as CORS-cross-origin"; Chromium implements it as `is_origin_tainted_` → silence; WebAudio issue #2453 confirms no detection/revert API exists; a 2026-05-07 gapless.js commit confirms `crossOrigin='anonymous'` must be set BEFORE `src` (C6).
5. **Visualisation architecture with measured cost exists**: AudioWorkletProcessor → SharedArrayBuffer ring buffer → Web Worker + OffscreenCanvas, main thread "less than 5% of one core" (Primozic 2023, [FULL]); AnalyserNode must be polled from the main thread (spec + Primozic); ScriptProcessorNode is DEPRECATED in the 1.1 draft; AudioRenderCapacity was REMOVED (TPAC 2024 decision, PR #2624) in favour of the WICG Playout Statistics API (C7, C8).
6. **three.js WebGPURenderer with automatic WebGL 2 fallback and TSL is the official direction** (threejs.org manual; `examples/webgpu_compute_audio.html` processes audio buffers with compute nodes and feeds an AnalyserNode `DataTexture` into `scene.backgroundNode`); `WebGLRenderer` gets no larger new features (C9).
7. **No music library ships an accessible waveform**: wavesurfer.js v7 (7.12.11, 2026-07-17; 8.0.0-beta.2 exists) renders a canvas in Shadow DOM with no ARIA/keyboard on the waveform; peaks.js (4.0.0-beta.2, 2025-05-13) has opt-in `keyboard: true` arrow-key scrolling only; g200kg webaudio-controls knobs have no ARIA attributes documented. The WAI-ARIA APG slider pattern (role=slider, aria-valuenow/min/max/text, arrows/Home/End/PageUp/PageDown) is the only standard, and there is no rotary role — a knob is an APG slider with `aria-valuetext` and explicit `aria-describedby` instructions (C10, C11).
8. **Academic evidence (4 papers [FULL]) says: surface intermediate structure, offer navigable levels of control, and make music glanceable**: DIS'25 (N=11+7) — vibe-first guidance + structured genre/instruments/mood/theme/energy refinement, 4/7 preferred it, musicians preferred direct prompting; CHI'26 VidTune (N=12) — contextual thumbnails made tracks significantly easier to understand (5.5 vs 3.33, p<0.05), compare (5.0 vs 3.0), remember (5.42 vs 3.17), and lowered temporal demand; 2AFC accuracy 88.2% vs 69.8% (p<0.001, d=1.60). Waveforms alone "do not convey perceptual qualities" (C12, C13).

# Five-part academic records (R9) — the four [FULL] papers

## A1. Buffa, Ren, Campbell, Burns, Yi, Kleimola, Larkin — "Web Audio Modules 2.0: An Open Web Audio Plugin Standard", WWW'22 Companion, pp. 364–369, doi:10.1145/3487553.3524225 [FULL]
1. **Problem (authors' framing):** the Web Audio API's built-in nodes are "too low level" for the plugin use-case; no official way to communicate with processors on the audio thread; AudioParam automation "conceived before developers had any direct access to the audio thread" and incompatible with synchronous "just in time" host↔plugin interaction; plugins must be Web resources (URIs), discoverable, dependency-conflict-free.
2. **Method:** WAM = WamNode (main thread) + WamProcessor (audio thread, extends AudioWorkletProcessor) pair; WamEnv singleton + WamGroups on the audio thread for host/subhost event graphs; descriptor.json + index.js ES module; `createGUI()` returns an HTMLElement; own WamParameter API (not AudioParam) with WamParameterInfo metadata; unified event scheduling mirrored on both threads (main-thread hosts need lookahead; audio-thread hosts schedule at block start); SDK: ParamMgr wraps AudioParams as WamParameters with mappings, CompositeNode wraps a subgraph as one node (extends GainNode). 4 MIT repos, npm `@webaudiomodules/*`.
3. **Quantitative results:** none — a systems/standards paper; no benchmark table. Stated facts: WAM created 2015; WAP 2018; WAM2 work started end-2020; AudioWorklet "supported by all major browsers in 2022"; presented to the W3C Audio WG/CG Dec 2021 and WAC 2021.
4. **Limitations:** authors: "still considered a 'beta version', but in a stable state". Analyst: no accessibility contract for GUIs; no performance numbers; host burden (WamEnv/WamGroup) undocumented in the paper.
5. **Application here:** adopt the headless-DSP + metadata-described-parameters + swappable-GUI split for THE WORLD station controls and the composer's 103-param panel: one typed parameter schema drives 2D (APG sliders) and 3D (three.js) controls, as WAC 2025 later did by introspection. Do not ship third-party WAMs.

## A2. Hwang & Marasco — "MILL: the Mobile Instrument Library and Launcher", WAC 2025, IRCAM Paris, 19–21 Nov 2025, CC BY 4.0 [FULL]
1. **Problem:** networked-music systems ship one instrument per show or leave instrument choice to performers; switching instruments requires redeploying code; composers want structural control while audiences want audible agency (Hödl et al.).
2. **Method:** browser-based library of mobile instruments (Web Audio API, RNBO, Tone.js) with audio engine and UI as separate layers; server (Collab-Hub protocols, WebSockets) registers devices, reconnects on drop, pushes instrument + performance-instruction payloads; three controller phases (design / registration / performance); Performance Instruction Layer occupies part of the screen and the Instrument Layer resizes proportionally; controller can constrain parameter ranges; example instruments: 4-voice chord generator (4 quality buttons, horizontal root slider, ADSR window, trigger button) and 3-voice pad synth (X=pitch, Y=timbre, 3 sliders for delay time/feedback/decay).
3. **Quantitative results:** none reported (no user study, no latency table). Design facts: user-initiated gesture required to enable audio; explicit "unmute your device" reminders; browser-compatibility notice per instrument.
4. **Limitations:** authors: server speed and participant scale; GUI design still requires web skills. Analyst: no accessibility of the touch widgets discussed; latency not measured.
5. **Application here:** the two-layer split (instruction layer that pushes the instrument layer to resize) is the pattern for our mobile composer: a collapsible "brief" strip above the controls; controller-constrained ranges = our per-genre parameter bounds; mandatory unlock gesture + unmute reminder + capability notice go into the player's first-play state.

## A3. Hammad, Fraser, Harpstead, Hammer, Dontcheva — "'It's more of a vibe I'm going for': Designing Text-to-Music Generation Interfaces for Video Creators", DIS'25, Funchal, doi:10.1145/3715336.3735814, CC BY 4.0 [FULL]
1. **Problem:** creators "struggle to describe their musical goals and compare options"; text-to-music models "often require musical expertise and are difficult to control"; keyword search is aimless.
2. **Method:** formative study N=11 (25-min interview + 25-min task walkthrough + 10-min interview; $30); design goals DG1–DG5 (rough-cut first; vibe-centred; video context; validate with video; structured exploration); prototype: select timeline region → LLM (GPT-4-Turbo 1106-preview) recommends an editable vibe from transcript (Speechmatics) + captions (CLIP/LLaVA) → LLM writes 3 structured prompts {genre, instruments, mood, theme, energy} → 3 tracks (custom instrumental T2M, ≤5 min) on 3 stacked tracks; refinement UI splits the prompt into 5 editable boxes; unchanged prompt → new seed, changed prompt → same seed; Previous/Next song navigation. Baseline: single text box, one song. User study N=7 (3 repeat), 2×20-min think-aloud (random order), 20-item 7-point survey (adapted CSI + Amershi guidelines), 40-min interview; $50.
3. **Quantitative results:** 85% of TikTok and 84% of YouTube videos contained music (2023, cited); 9/11 began the "music supervisor" description with a narrative overview; all 11 used the word "vibe"; 4/7 preferred the probe, 2/7 both, 1/7 (most musically expert) critical of both; survey visualised only ("small sample size makes statistical testing inappropriate"); probe rated clearer feature set (Fig. 9).
4. **Limitations:** authors: N small, one model, no comparison to existing search workflows, song-level control only, same-seed does not guarantee similarity. Analyst: participants recruited inside a large tech company (Adobe) for the user study; instrumental-only model.
5. **Application here:** (a) composer default = editable "vibe" line (our brief line already exists) that expands into the structured fields the engine actually takes; (b) offer two modes — guided (structured chips) and open (free text) — and let users move between them (§6.3); (c) preserve seed on small edits and change seed on "regenerate as-is"; (d) render ≥3 takes at once for exploration.

## A4. Huh, Fraser, Li, Dontcheva, Wang — "VidTune: Creating Video Soundtracks with Generative Music and Contextual Thumbnails", CHI'26, Barcelona, arXiv:2601.12180, doi:10.1145/3772318.3791572 [FULL, references excluded]
1. **Problem:** creators "struggle to construct diverse prompts, quickly review and compare tracks, and understand their impact on the video"; default titles/thumbnails uninformative ("Untitled"), forcing sequential listening; DHH creators lack cues.
2. **Method:** formative N=8 (30-min task in Suno; avg 15 tracks generated, SD 5.44; 3 DHH). D1–D5.
