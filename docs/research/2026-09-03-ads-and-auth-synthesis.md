# Decision served

Which ad stack to integrate on the web page and the Flutter apps (item 2), and which authentication architecture to build so that PlayMusicPrompts has its own user database plus Google and Amazon sign-in at `auth.playmusicprompts.com` for web and mobile/tablet (items 3–5).

# Outcome first

**Ads (E).** Google is the only network the product can enter today without a traffic gate; every alternative is gated (Ezoic 250,000 monthly users since 2026-02-19; Raptive 25,000 pageviews + ≥50 % Tier-1 traffic + 6-month domain; Mediavine $5,000/yr, Journey 1,000 sessions; audio networks AdsWizz/Triton/Audiomob/Odeeo contract-only) [E-1 S28–S31, S38–S42]. Two policy facts shape the plan: (1) AdSense Publisher Policies forbid Google ads on "screens without publisher-content or with low-value content" — the one-prompt player page is that shape, so the application is filed only after the public `/musics` catalogue and About/Contact/Privacy/Terms pages exist [E-1 S01, S02]; (2) personalised ads in the EEA/UK need a Google-certified TCF CMP since 2024-01-16 — our `consent.js` does not qualify; use Google's certified CMP (ID 300) on web and the UMP SDK in the app, no new vendor [E-1 S06, S03]. Mobile: `google_mobile_ads` 9.1.0 (2026-08-12; minSdk 24, compileSdk 36, Flutter ≥ 3.38.1); ads may not run in background; interstitials only at logical breaks (track boundary), never at load/exit; rewarded "one more generation" is compliant as a non-monetary, opt-in, disclosed top-up that never gates the free quota [E-1 S11, S12, S17–S20]. Listener evidence: Pandora RCT (35 M listeners, 21 months): −2.08 % hours and −1.91 % active days per +1 ad/hour; 40 % of the loss is churn; long-run effect ≈ 3× the one-month estimate; listeners prefer shorter, more frequent breaks [E-1 S25 FULL]. Economics: a banner refreshing every 60 s for a 10-minute session needs ≈ $24 eCPM to cover one 3-take round ($0.24) versus $0.50–1.50 reported (secondary, unverified); one rewarded view ≈ 19–38 % of one take at Tier-1 eCPMs → ads are a partial offset; the cost base is covered by the reuse catalogue (A–D) plus quotas [E-1 §Item 5, CALCULATION]. Türkiye payout supported (₺200 threshold) [E-1 S05, S14–S16].

**Auth (F) — committed: Ory Hydra + our own Next.js login/consent app at `auth.playmusicprompts.com`, users in our Postgres 16, Google and Amazon brokered server-side; Flutter = public OIDC client with PKCE via `flutter_appauth`, claimed-https App Links / Universal Links (RFC 8252 §7.2).** Reasons: Berk's order names a dedicated auth host and "most advanced and secure" for web AND mobile; RFC 9700 requires PKCE for public clients and rotated or sender-constrained refresh tokens; only a real authorization server issues discovery, `/authorize`, `/token`, rotation and revocation to the apps from ONE issuer. Hydra has no user store of its own ("delegates the login flow to another app"), so the existing Prisma `users`/`accounts` tables remain the directory — "own database" by construction [F-1 S17; F-2 S-12↔L-01]. Hosted IdPs (Cognito, Identity Platform, Auth0, Clerk, Supabase) own the directory and/or are paid → rejected [F-1 S07–S11; F-2 S-19–S-28]. Google's native-app doc (2026-08-07): custom URI schemes unsupported on Android, loopback deprecated on mobile → brokering through our AS means Google only ever sees a Web application client [F-1 S04; F-2 S-05].
